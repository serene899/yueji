# 阅迹 · 项目总说明与进度（给外部评审用）

更新：2026-11-21 · 当前版本 v0.3.0（已上线）· 维护：Atlas

## 一、项目定位

阅迹是 LIFEOS 个人生活数据系统中的一个子应用：一座**只属于用户自己的精神文化档案**，记录读过什么、看过什么，以及这些作品在不同时间带给自己的感受。

产品红线（已确认，不要推翻）：
- 不做社交：没有点赞、关注、排行、分享；
- 数据本地优先：全部数据只存用户手机浏览器（IndexedDB），无服务器、无账号、不联网发送；
- 同一作品可以有多次记录并存——感受随时间的变化本身就是档案价值；
- 与 LIFEOS 人生K线图的交换只送「事实」（读书时长、文化活动条数），绝不送感受/摘句原文，阅迹不给任何东西打分；
- 数据结构只做「可选加键」式扩展，不删已有字段、不让旧数据失效。

技术栈：React 18 + TypeScript + Vite + Dexie(IndexedDB) + Tailwind CSS + vite-plugin-pwa，部署在 GitHub Pages，iPhone Safari 为主要使用环境。

## 三、当前功能（按页面）

- **首页**：概览计数（书/剧/电影/记录/收藏句，按馆藏总数计）；正在阅读（页码进度+封面）；正在追剧（集数进度+封面）；最近观影（电影+电视剧的最近记录）；最近记录（全部类型）。
- **书架**：四种类型统一列表，类型筛选、状态筛选、按名称/创作者搜索，按最近更新排序；每项显示封面（无图自动生成按类型配色的「素封面」）、状态标签、进度条。
- **作品详情**：封面大图、基本信息、状态/起止日期/印象深刻标签、累计时长；进度卡（书：页码，剧：集数）；收藏句子墙；完整记录历史（点按可编辑）。
- **年度回顾**：读完的书（按完成日期）、追过的剧、看过的电影（按当年有记录或完成日期）、记录条数、收藏句数、总时长、每月记录柱状图、印象深刻清单、年度小结句。
- **我的**：数据说明、备份导出/导入恢复、LIFEOS 交换导出。

作品字段：类型（书/电视剧/电影/其他）、名称、创作者、分类、年份、总页数（书）、片长（电影）、总集数（剧）、状态（计划中/进行中/已完成，按类型显示为想读/在读/读完等）、开始日期、完成日期、印象深刻、封面图。
记录字段：所属作品、日期、读到页码（书）、看到集数（剧）、时长（分钟）、感受、收藏句子/台词。

## 四、核心业务逻辑（现状口径，逐条如实）

1. **进度**：书的进度 = 所有记录中最大页码 ÷ 总页数；剧的进度 = 最大集数 ÷ 总集数；没有总页数/总集数就不算进度（只显示记录）。状态为「已完成」时进度强制显示 100%。
2. **状态联动（记记录时自动发生）**：
   - 书：第一条记录 → 计划中自动变「在读」并补开始日期；某条记录页码 ≥ 总页数 → 自动变「读完」并以该记录日期为完成日期。
   - 剧：第一条记录 → 自动变「在看」；集数 ≥ 总集数 → 自动「看完」。
   - 电影：第一条记录 → 直接自动「看完」（假设一次看完）。
   - 其他：第一条记录 → 自动变「进行中」，完成靠手动。
   - 联动只进不退：之后编辑/删除记录把页码改小、把关键记录删掉，状态不会自动退回。
3. **完成日期**：在作品表单里把状态设为「已完成」而没填完成日期时，自动填今天。
4. **年度回顾口径**：读完的书只看完成日期是否落在该年（不校验当前状态）；剧和电影看「该年有记录」或「完成日期在该年」二者其一（同一作品可能在两个年份都出现）。
5. **LIFEOS 交换口径**：读书时长只统计书籍记录的分钟数；文化活动条数统计全部类型的记录（含电视剧、其他）。
6. **备份**：JSON v2，封面转 base64 内嵌；导入先全量校验，通过后整库替换（有二次确认）；兼容 v1 旧备份。

## 五、开发者自查的「逻辑可疑点」（请重点评审）

所有者反馈「感觉逻辑上有点问题但说不清」，以下是开发方自查出的候选问题，请逐条判断是否成立、该怎么改：

- **Q1 状态与进度可能互相矛盾**：联动只进不退 + 完成强制 100%，会出现「状态是读完、进度条 100%，但记录里明明只读到第 80 页」；删掉读完的那条记录后，状态仍是读完。状态到底应该由记录推导，还是独立维护？
- **Q2 年度口径不对称**：书按完成日期、剧和电影按记录或完成日期，一部跨年追的剧会在两年都算「追过」，一本跨年读的书只在读完那年算数。口径要不要统一？统一成哪种？
- **Q3 年度「读完的书」不看当前状态**：一本书标过读完又改回「在读」，年度里仍算它读完（因为只看完成日期字段）；且状态改回未完成时完成日期不会自动清除，会一直残留。
- **Q4 电影的自动完成假设**：电影记第一条记录就自动「看完」，但用户可能只是记了个预告片感受、或分两次看。电影到底需不需要「在看」状态？
- **Q5 概览计数口径**：首页「1 本书」是馆藏总数（含想读的），用户可能直觉理解为「读了 1 本」。概览该报馆藏、完成数，还是分开报？
- **Q6 进度只能靠记录推进**：作品表单里不能直接改「读到第几页」，想补进度必须新建一条记录（哪怕没有感受要写）。这是有意保持「进度必有记录」，还是应该允许直接改进度？
- **Q7 时长统计偏斜**：年度总时长把各类型记录的分钟数直接相加，但电影记录常不填分钟（片长在作品上），导致电影时长被系统性低估。时长要不要按作品片长兜底？
- **Q8 重复作品无提示**：同名作品可以重复添加，记录会散在两条里，统计各算各的。要不要在添加时提示疑似重复？
- **Q9 文化活动口径（已向所有者报备）**：电视剧/其他记录现在计入发往人生K线图的「文化活动」条数。这个口径是否合理，还是应该只计书和电影？
- **Q10 「其他」类型的完成**：其他类型永远不会自动完成，全靠手动改状态；且「其他」里混了音乐、播客、演出、游戏，年度回顾不单独统计它们（只进总记录数）。这个兜底设计是否够用？

## 六、已知问题与未做事项

- 应用图标 PNG 因 GitHub 推送通道限制未上线（三个 LIFEOS 子应用通病），主屏幕图标可能显示默认样式，不影响功能；
- 封面只能从相册手动选图，没有联网搜封面（版权与来源问题，未擅自做）；
- 没有评分功能（定位如此，未计划加）；音乐等专门类型未拆分，先由「其他」兜底；
- 与人生K线图是文件接力（用户手动导出/导入），没有自动同步（iOS 存储隔离未验证，暂不做）。
